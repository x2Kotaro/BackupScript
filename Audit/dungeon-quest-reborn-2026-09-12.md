# Dungeon Quest Reborn — security audit

Date: 2026-09-12
Place: `[+1 DROP + 2x LUCK] Dungeon Quest Reborn` — PlaceId 77649408247578, JobId 2bb1f85e-49f3-4d86-801d-d2ba7a70b929
Method: read-only recon via the Dex MCP bridge (client-side tree walk, decompile, remote spy, safe GET probes). No mutating remote was fired with crafted args; no live economy state was changed.

## 1. Anti-cheat map

| Control | Location | Client- or server-side | Notes |
|---|---|---|---|
| **RemoteGuard** — schema-validated remote binder | `ServerScriptService.DataStorage.RemoteGuard` (not client-visible; contract inferred from `timeSync`'s usage) | **Server-side** | `RemoteGuard.Bind(remote, schema, handler)`. Confirmed schema: `{{"number", min=0, max=1000000000000}}` for `DelayedRequestEvent`. Real validation exists, but see Finding 3 — the bound used here is too wide to reject implausible values. |
| **Executor-call response spoofing** | Server response to `InvokeServer` from a detected executor environment | **Server-side** | Confirmed live: `getPlayerStorage`, `getData`, `getDungeonStats` all returned the **remote's own Instance path as a string** instead of real data when called from this bridge (caller tagged `From: "Opiumware"` by the spy hook, i.e. server saw a non-standard calling environment and handed back a decoy rather than erroring or yielding). This is a real, working control — it silently launders exploit calls into junk data instead of tipping off the caller. Could not get past it with read-only probing, which is the intended outcome. |
| **MasterClock / SlaveClock** (`ReplicatedStorage.timeSync`) | Server keeps authoritative `tick()`, broadcasts every 5s via `TimeSyncEvent`, client requests round-trip delay via `DelayedRequestEvent:InvokeServer(localTime)` | **Server-side clock, client-supplied round-trip arg** | Server computes `serverTime - clientTime` on every request and hands the client an `_offset`/`_pneWayDelay` used only for client-side display/animation. | **CmdrPermissions** (`ReplicatedStorage.CmdrPermissions`) | Admin console (Cmdr) role/rank gate | Logic replicates to client, but gates on `Player:GetRoleInGroup`/`GetRankInGroup` — real Roblox group API calls, not client-supplied data. **Not spoofable from the client** as long as the server-side Cmdr dispatcher calls this module with the authentic server `Player` instance (standard Cmdr architecture; could not confirm the dispatch call itself, which lives server-side). | See Finding 4 for one broad bypass path (`"Transfer"` server type) worth double-checking. |
| **Cmdr admin commands** (`wipeData`, `resetEventData`, `activateRPOEvent`, `ban`/`kick`/etc.) | `ReplicatedStorage.CmdrClient.Commands.*` | Client-visible definitions only — these are just Cmdr command *descriptions* (help text, arg parsing) that ship to every client so the console can autocomplete them. Actual execution and permission check happen server-side through Cmdr's dispatcher + `CmdrPermissions`. Seeing the command names client-side is normal Cmdr behavior, not itself a hole. |

**Why detections fire (answering "ทำไมโดนยิง"):** the one concretely observed server-side control is the InvokeServer response-spoofing behavior above. A client whose environment gets flagged there gets fed decoy data on every `getData`/`getPlayerStorage`/`getDungeonStats` call — it doesn't "kick" visibly, it just quietly starves the exploit of real state. If a kick/ban *did* happen historically, the most likely trigger is this same detection escalating (repeated decoy-triggering calls, or a companion check inside `RemoteGuard`/`DataStorage` we cannot see from the client) — not a client-side check, since none of the client-visible modules examined (`CmdrPermissions`, `timeSync`, `touchDetection`) perform bans or kicks themselves.

## 3. Findings

### Finding 1 — Executor-response spoofing confirms detection, but only 3 of 190 remotes were probed (Confidence: confirmed for probed remotes)
**Severity:** Informational (this is a working defense, not a hole) — flagged so it isn't mistaken for a gap.
`getPlayerStorage`, `getData`, `getDungeonStats` all return a decoy string (their own Instance path) instead of real data when invoked from a caller the server fingerprints as an executor. This means naive automated probing of *these three* remotes cannot retrieve real player state or be used to enumerate schema. It does **not** prove the other 187 remotes carry the same protection — each `RemoteFunction`/`RemoteEvent` is bound independently, and coverage should be spot-checked (fire a couple of the mutating ones from a private/test server the developer controls, with a throwaway account, and confirm the same decoy/refusal behavior — not on a live shared server).

### Finding 2 — `selectRecoveryOption:FireServer(optionName: string)` sends an unvalidated string picking a data-recovery action (Confidence: plausible, not confirmed)
**Flow:** `StarterPlayer.StarterPlayerScripts.DataRecovery.touchDetection` — reachable only inside the dedicated "DataRecovery" place (gated by `PlaceManager.GetPlaceName() == "DataRecovery"`), triggered by touching `workspace.button.touchPart`. On button click it fires `ReplicatedStorage.selectRecoveryOption:FireServer(v_u_5.Name)`, where `v_u_5.Name` is the **Name of a Frame instance built client-side** — i.e. the argument is whatever string is on the GUI button the player clicked, and nothing stops a modified client from firing this remote directly with an arbitrary string instead of clicking through the UI.
**What a crafted arg would do:** unknown from the client side — depends entirely on how `ServerScriptService` handles the option name (a lookup table keyed by name, presumably). If that lookup isn't bounds-checked (e.g., indexes an array/table without validating the key exists, or matches on a wildcard/prefix), a crafted option name could select an unintended recovery branch (e.g., "recover everything" instead of the intended narrower option), which is exactly the shape of the rollback abuse being asked about.
**Fix:** validate `optionName` server-side against an explicit whitelist of the exact button names the place currently ships (not just "does the key exist" — enumerate); rate-limit/single-use per session (the client already debounces via `v_u_1` but that's client-side only, so the server needs its own one-shot guard per player per recovery session); log every recovery selection with player id + chosen option + server timestamp for after-the-fact audit.
**To confirm:** would need either the server script (not visible from client) or to trigger the flow in a private/test server and observe the actual inventory delta per option.

### Finding 3 — Client-supplied timestamp in `DelayedRequestEvent` is accepted across a near-unbounded range, and observed client/server clock values differed by ~4.7 hours in this session (Confidence: confirmed for the range check; the specific 4.7h gap needs a second look)
**Flow:** `timeSync`'s `SlaveClock:_sendDelayRequest` calls `DelayedRequestEvent:InvokeServer(localTime)` where `localTime = tick()` on the *client*. Server's `MasterClock._handleDelayRequest(player, clientTime) return serverTime - clientTime` — this value only feeds a client-side display offset in the code that's visible, so on its own it's low severity. It matters as a **pattern**: `RemoteGuard`'s bound for this argument is `min=0, max=1000000000000` — i.e. it accepts any Unix timestamp from 1970 up to the year ~33658. That is not "validate this is a plausible current timestamp," it's "validate this is a positive number." Any other server code that trusts a client-supplied timestamp (e.g., "when was this action performed," used for save-ordering or a recovery/rollback window) would pass through the same style of check and accept a frozen, replayed, or future value.
**Observed data point:** during this session, `TimeSyncEvent` (server broadcast) reported `~1789210689–1789210754` (5s apart, monotonic — looks correct), while the client's own `DelayedRequestEvent` argument (its `tick()`) reported `~1789193822–1789193887` — a **consistent ~16,867 second (4.7 hour) gap**, stable across the whole session rather than drifting. That's large enough that it's unlikely to be simple clock skew; it's worth checking whether the executor environment is normalizing/hooking `tick()` (which would make this an artifact of the test rig, not the game) versus the server's `tick()` running on a different epoch reference. Either way, note that this delta was accepted by the server without complaint — nothing in `_handleDelayRequest` sanity-checks that the client's timestamp is even in the right decade.
**Fix:** if any save/rollback/recovery logic anywhere in `DataStorage` keys off a client-reported timestamp rather than a server-generated one, that's the exact hole matching "ช่องโหว่ของ Timestamp" — switch to a monotonic server-side clock/sequence number for anything that decides which save is "newer," and never let a client argument decide save ordering. For `DelayedRequestEvent` specifically, tighten the schema to `max = os.time() + smallSlack` computed at bind time isn't possible statically, but the handler itself can reject `math.abs(serverTime - clientTime) > someThresholdSeconds` before using it for anything beyond a rough display estimate.

### Finding 4 — `CmdrPermissions.hasCommandAccess` / `canRunCommandOn` grant a broad bypass when `PlaceManager.GetExperienceIndentifier(game.PlaceId) == "Transfer"` (Confidence: plausible, needs access-scope confirmation)
On a place classified as `"Transfer"`, `hasCommandAccess` returns `true` unconditionally for the ban/unban/kick moderation check path is skipped (falls through to `true` before the group-rank lookup even runs), and `canRunCommandOn` restricts a non-moderator to "commands on yourself only" rather than denying outright. This is presumably intended for whatever internal data-migration/transfer place this identifier marks, and is fine **if that place is not player-reachable**. Worth confirming `PlaceManager`'s definition of "Transfer" places and that they're not exposed to the general player base — if a regular game server can ever satisfy that identifier check, it's an unintended admin-console bypass.

## 4. What wasn't covered (limitations)

- **Server-side code is entirely opaque from this vantage** — `ServerScriptService` returns zero children to `dex_tree` from the client, as expected. Every finding above about server behavior is inferred from remote contracts, client-visible modules that `require()` server modules by reference (like `timeSync` referencing `RemoteGuard`), and observed effects — not from reading the actual validation code.
- **No inventory/trade/purchase traffic was captured** — this session's spy window didn't include a manual play-through of pickup → equip → sell → trade → rejoin. Re-run Phase 2 with that play-through to fill in the economy remotes' actual argument shapes and confirm/deny unvalidated-arg findings against real traffic instead of just the exposed remote names.
- **The two-client dupe scenario cannot be fully observed from one session** — proving an actual rollback/dupe (mutate → disconnect before save → rejoin with old state restored) needs either a second account or a controlled private-server test, not just this client's spy log.
- **Nothing in this audit fired a mutating remote with a crafted or out-of-contract value.** Recon stayed read-only per the audit's own rules; the findings above are what to check next in a private/test server, not confirmed exploits.

## 5. Addendum — Finding 5: `purchaseCase`/`awardCaseCosmetic` rollback dupe (Confidence: **confirmed**, mechanism read directly from client source)

The user supplied a working rollback script's behavior description ("keep ticked rewards; rejoin before the roll ends on anything else, so no gems are spent") and asked where to look. Traced it to `Players.<user>.PlayerGui.mainInterface.shop.crates.CaseScript` (same script ships at `StarterGui.mainInterface.shop.crates.CaseScript`). The client source confirms the exact mechanism:

**The flow, in order:**
1. Client fires `remotes.purchaseCase:FireServer(caseName)`. The server decides the roll and (per `PlayerValues`, Finding-3-adjacent) debits gems **in-memory** at this point — nothing observed from the client shows this being persisted immediately.
2. Server replies via `casePurchaseResult.OnClientEvent(payload)` where **`payload` already contains the final result** — `payload.cosmetic`, `payload.cosmeticType`, `payload.rarity`, and a `payload.transactionId`. The roll is already decided and the currency is already spent server-side before any animation starts.
3. Client calls `getCaseCosmetics:InvokeServer(caseType)` to fetch the cosmetic pool (visual data for the spin reel only — the actual reward is already fixed from step 2) and runs a purely cosmetic client-side spin animation (`DoSpin`).
4. **Only when the spin animation finishes** does the client fire `remotes.awardCaseCosmetic:FireServer(item.name, item.type, transactionId)` — this is what actually causes the server to commit the cosmetic into the player's persistent inventory.

**The hole:** steps 1–2 (spend + roll) and step 4 (grant) are two separate server calls, separated by a delay that is entirely **client-controlled** (the spin animation's duration, `DoSpin`, running client-side). A modified client can disconnect between step 2 and step 4 — i.e., during its own animation, before ever sending `awardCaseCosmetic`. Because:
- the cosmetic grant never happens (server is waiting on a client message that never arrives), and
- the currency debit from step 1 lives only in server memory (`PlayerValues.SetValue`/`IncrementValue`, no persistence call visible anywhere in this framework) until whatever periodic/leave-triggered save exists in the opaque `DataStorage` script runs,

a disconnect fast enough to beat that save discards the entire in-memory delta. On rejoin, DataStore still holds the pre-purchase gem balance — the roll is undone, the spend is undone, and the *cost* of finding out what the roll would have been was zero. This matches the reported script's behavior exactly: ticked (wanted) rewards are simply allowed to finish normally (`awardCaseCosmetic` fires, cosmetic + spend both eventually persist together); anything else triggers a disconnect inside that window, refunding the attempt.

Notably, the server **does** have a `transactionId` correlating the purchase to the claim — that's good practice for idempotency (stops the same claim being replayed twice), but it does nothing to prevent the claim from simply never arriving.

**Fix — pick one:**
- **Preferred:** collapse purchase + grant into one atomic server operation. Roll the result and write the cosmetic into the player's persistent inventory in the *same* handler that debits currency (`purchaseCase`), before `casePurchaseResult` is ever sent to the client. Let the client's spin animation just be a presentation of an already-committed result — remove `awardCaseCosmetic` as a gate for anything that matters server-side (it can still fire for telemetry/UX, just not as the only path to the grant).
- **Minimal, if the two-phase design has to stay:** on `PlayerRemoving`/`BindToClose`, reconcile any `purchaseCase` transaction that was issued but never confirmed via `awardCaseCosmetic` — auto-grant the pending cosmetic instead of silently dropping it. That makes "disconnect mid-spin" behave identically to "let the spin finish," closing the free-reroll window without changing the UX for honest players.
- Either way, this reinforces Finding 3: any currency/reward flow in this codebase that debits before a guaranteed-synchronous persist point is exploitable this way. `purchaseCase` is the confirmed instance; `requestGoldGamepassPurchase`, `requestGoldXPBoostPurchase`, `requestPackPurchase`, `upgradeItem`, `upgradeKey`, and `purchaseCosmetic` share the same remote-pair shape (spend remote + separate result/grant path) and should be checked for the same split.
